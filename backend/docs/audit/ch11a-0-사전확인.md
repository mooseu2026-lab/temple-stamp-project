## STEP 3 — 저장소 구조

### `ObjectStorageClient` public 메서드 전부

| 메서드 | 하는 일 |
|---|---|
| `String createFileKey(UploadPurpose, Long userId)` / `(…, String ext)` | `{PURPOSE}/{userId}/{uuid}.{ext}` |
| `Presigned presignPut(String fileKey)` | `{fileKey, url, expiresInSeconds}` |
| `String presignGet(String fileKey, long seconds)` / `(String fileKey)` | 다운로드 서명 URL |
| `long getPresignSeconds()` | 설정값 |
| `void verifyOwnedKey(String fileKey, UploadPurpose, Long userId)` | 키가 **내 것인가** — 3토막 · PURPOSE 일치 · userId 일치 · `..` 금지 |
| `void put(String fileKey, byte[], String contentType)` | 로컬 디렉터리에 쓴다 |
| `byte[] getBytes(String fileKey)` · `boolean exists(String)` · `void delete(String)` | 로컬 디렉터리 |

### provider 분기는 **없다**

`storage.provider` 를 읽는 코드는 저장소 전체에서 **`RequiredEnvCheck` 한 곳뿐**이고, 하는 일은 "local 이 아니면 기동을 막는다" 다.

```java
// RequiredEnvCheck — ObjectStorageClient 는 provider 값을 읽지 않고 언제나 로컬 디렉터리에 씁니다.
if (provider == null || provider.isBlank() || "local".equalsIgnoreCase(provider.trim())) { return; }
throw ... "storage.provider=" + provider + " 는 미구현 — local 만 지원합니다."
```

`ObjectStorageClient` 안에 `if (local)` 같은 갈래가 없다 — **네 메서드(`put`·`getBytes`·`exists`·`delete`)가 곧 local 구현**이고, S3 로 갈 때 그 넷과 `buildUrl`/`sign` 을 바꾸는 것이 설계다(클래스 주석에 그렇게 적혀 있다).

### presign 서명

```java
// 규격: HMAC-SHA256(  method \n bucket \n fileKey \n expiresAt  ), 키는 storage.secret-key
private String sign(String method, String fileKey, long expiresAt) { … }
private String buildUrl(String method, String fileKey, long expiresAt) {
    return "%s/%s/%s?expires=%d&signature=%s".formatted(endpoint, bucket, fileKey, expiresAt, urlEncode(sign(...)));
}
```
키 출처는 **`storage.secret-key`**(= `${STORAGE_SECRET_KEY:local-storage-secret}`). 서명을 **검증하는 코드는 저장소에 없다** — 검증 주체가 운영의 S3 라고 보고 만들었기 때문이다(보안 검사 S24 도 그 사실을 그대로 적고 넘어간다).

### 실태 — 사진 바이트는 어디에도 없다

| 확인 | 결과 |
|---|---|
| `presign` 이 주는 `uploadUrl` | `http://localhost:9000/temple-stamp-local/PHOTO/44944/…jpg?expires=…&signature=…` |
| `http://localhost:9000` | **연결 실패**(응답 000). 그 자리에 서버가 없다 |
| `…/temple-stamp-storage/PHOTO/` | 디렉터리는 있고 **파일 0개** |
| `…/EBOOK/` · `…/CERT/` | 2개 · 1개 — 서버가 `put()` 으로 직접 쓴 것들 |

즉 **사진은 지금까지 키만 기록되고 바이트는 한 장도 저장된 적이 없다.** 전자책 조판이 사진을 못 찾으면 "(사진 없음)" 으로 넘어가도록 만들어 둔 것이 이 상태를 덮고 있었다(`PdfBuilder.addPhoto`).

### 판정

> ## **11-A STEP 4 의 "PUT /api/uploads/{fileKey}" 는 가능하다 (✅)**

- **local 분기에만 붙는가** — 붙일 분기 자체가 없지만, 그 문이 하는 일(`storageClient.put`)이 이미 local 전용 메서드다. S3 로 바꾸면 그 문은 **쓰이지 않게** 된다(프론트가 S3 로 직접 올린다).
- **프론트 계약이 안 바뀌는가** — 바뀌지 않는다. `presign` 응답의 두 필드(`uploadUrl`·`fileKey`)가 그대로다. `storage.endpoint` 를 우리 앱 주소로 두면 `buildUrl` 이 만드는 URL 이 그대로 이 문을 가리키고, S3 로 갈 때는 `endpoint` 만 S3 주소로 되돌리면 된다. **프론트는 언제나 "받은 uploadUrl 로 PUT" 하나만 한다.**
- 다만 **서명 검증 코드를 처음으로 쓰게 된다.** 지금까지 `sign()` 은 만들기만 하고 검사한 적이 없다 — 11-A 는 같은 규격으로 `expires`·`signature` 를 다시 계산해 비교하면 된다(키·정규 문자열이 한 함수에 모여 있어 재사용이 쉽다).

**기능.md §1-4 사진 행의 저장소 문구 — 수정 초안(11-A 완료 후)**

| | |
|---|---|
| 원문 | `presigned URL로 저장소 직접 업로드(서버는 바이트 안 받음)` |
| 수정문 | `presign 으로 받은 uploadUrl 에 직접 PUT — 지금은 그 URL 이 우리 앱의 PUT /api/uploads/{fileKey} 를 가리킨다(provider=local). S3 로 바꾸면 같은 필드가 S3 주소가 되고 프론트 코드는 그대로다` |

자가 검증 셋을 넣었다 — 코드 중복 0 · 모양(`도메인-4자리`) · **코드의 앞 세 자리와 HTTP 상태가 같은가**(`REWARD-4092` ↔ 409). 셋 다 어긋남 0.

> **만들면서 한 번 틀렸다.** 처음에는 enum 본문을 `첫 '{'` 부터 `첫 ';'` 까지로 잘랐는데, 클래스 주석 안에 `{도메인}_{HTTP 상태 3자리}` 라는 중괄호가 있고 첫 세미콜론은 `package` 선언의 것이라 **잘린 구간이 비어 0개**가 나왔다. `public enum ErrorCode {` 와 `private final int status;` 를 닻으로 바꿔 79개가 되었다. 79 단언이 없었으면 "0개" 를 성공으로 지나갔을 자리다(§6-11).
