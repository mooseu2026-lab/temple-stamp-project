## 1부. GPS / 3단계 인증

### 1-1. 잘 되어 있는 것 (근거 포함)

이건 문제가 아니라, "잘 되어 있는지"를 물었으니 왜 잘 되어 있다고 판단했는지 근거를 남긴다. 나중에 누가 건드릴 때 이 부분은 이유 없이 바꾸면 안 된다.

**(a) 좌표를 안 받는 원칙 — 3중 방어**

| 층 | 어디 | 어떻게 |
|---|---|---|
| DTO | `GpsCheckRequest` record | 필드가 siteId·withinRadius·accuracyGrade 셋뿐. Jackson은 모르는 필드를 기본적으로 무시하지만, 그 전에 아래 필터가 잡는다 |
| 필터 | `CoordinateFieldGuard @Order(-105)` | POST/PUT/PATCH + JSON 본문을 재귀 스캔. `{"a":{"b":[{"LAT":1}]}}`처럼 깊이 숨겨도 잡는다. 대소문자 무시. 컨트롤러에 닿기 전에 400 COMMON-4001 |
| DB | `stamp` 표 | 위경도 컬럼 자체가 없다. 저장하려 해도 못 한다 |

화이트리스트는 `/api/admin/sites/**` 하나. 사찰 좌표는 시설 위치라 개인정보가 아니다. 판단이 맞다.

**(b) 상태 기계 — 자바와 SQL 이중 검사**

```java
// StampService.verifyQr — 자바 검사
if (stamp.getVerifyStatus() != StampStatus.GPS_DONE) throw ... STAMP_4092
```
```sql
-- StampMapper.markQrDone — SQL 검사
WHERE stamp_id = #{stampId}
  AND verify_status = 'GPS_DONE'
  AND gps_verified_at >= DATE_SUB(NOW(), INTERVAL #{sessionMinutes} MINUTE)
```

왜 두 번 하는가: 자바 검사와 UPDATE 사이에 다른 요청(청소기 배치, 같은 사용자의 중복 탭)이 끼어들 수 있다. 자바가 "GPS_DONE이다"라고 본 뒤 0.1초 뒤에 배치가 EXPIRED로 바꾸면, 자바 검사만 있으면 EXPIRED 행 위에 QR_DONE을 덮어쓴다. SQL WHERE가 있으면 영향 행 0 → STAMP_4091. "읽고 나서 쓰는 사이의 틈"을 SQL로 닫은 것이고, 이게 이 코드의 가장 좋은 부분이다.

`markGpsDone`도 `verify_status IN ('GPS_DONE','QR_DONE','EXPIRED','REJECTED')`로 제한해서 COMPLETED·PENDING 행은 절대 되돌릴 수 없다.

**(c) QR 토큰**
- HMAC-SHA256. `QR_SECRET != JWT_SECRET`을 생성자에서 검사해 다르지 않으면 빈 생성 실패 → 서버가 안 뜬다. 배포 뒤 발견되는 게 아니라 뜨기 전에 막힌다.
- 서명 검증을 payload 파싱보다 먼저 한다. 위조 토큰의 payload를 먼저 파싱하면 NumberFormatException 같은 엉뚱한 예외로 500이 나거나, 파싱 로직 자체가 공격 표면이 된다.
- `MessageDigest.isEqual` — 일반 equals는 첫 바이트가 다르면 바로 false를 돌려줘서 응답 시간 차이로 서명을 한 바이트씩 맞출 수 있다(타이밍 공격). isEqual은 길이만큼 항상 다 비교한다.
- `qr_version`을 서명에 포함 → 사찰 QR 사진이 유출되면 `site.qr_version +1` 하나로 그 절 QR 전부 무효. 종이 회수 전에 피해를 끊는다.
- 오류 코드가 상황별로 다르다: 4002 위조/형식 · 4003 만료 · 4004 다른 절. 사용자에게 "다시 찍으세요"와 "여기 QR이 아닙니다"는 다른 안내다.

**(d) v4 후보 사찰**

1단계에서 `slotSiteMapper.exists(courseSiteId, siteId)`로 후보 검증 후 `stamp.site_id`에 박고, 2단계에서 `stamp.getSiteId()`의 QR만 허용한다. 후보 A에서 도착 확인하고 대표 B의 QR로 통과하는 경로가 막혀 있다. 이걸 놓치기 쉬운데 잡았다.

**(e) 만료와 잠금 순서**

`expireOrThrow`(REQUIRES_NEW로 EXPIRED 커밋)를 행 잠금 전에 부른다. 잠근 뒤에 부르면 바깥 트랜잭션이 쥔 행을 안쪽 트랜잭션이 기다리다 자기 자신과 교착 → 50초 뒤 500. 주석에 "정정(2026-09-06)"이라고 적힌 걸 보면 실제로 당하고 고친 것이다.

**(f) 인가**

stamp에 user_id가 없어 `pilgrimage.user_id`로 소유 확인(`requireOwner` → STAMP_4031). userId는 `@AuthenticationPrincipal`에서만. 원칙 1·3 준수.

### 1-2. 문제 ① `findLastCompletedSiteId`가 대표 사찰을 돌려준다

**현상** — `StampMapper.xml` 272행:
```sql
<select id="findLastCompletedSiteId" resultType="long">
    SELECT cs.site_id                        -- course_site.site_id = 그 자리의 "대표" 사찰
    FROM stamp st
             JOIN course_site cs ON cs.course_site_id = st.course_site_id
    WHERE st.pilgrimage_id = #{pilgrimageId}
      AND st.verify_status = 'COMPLETED'
      AND st.mission_verified_at IS NOT NULL
    ORDER BY st.mission_verified_at DESC
    LIMIT 1
</select>
```
`StampService.submitMission` 210행:
```java
// v4 — 이동시간도 대표가 아니라 실제로 인증한 사찰 사이의 거리로 잰다
Integer shortfall = travelTimeShortfall(stamp.getPilgrimageId(), stamp.getSiteId());

private Integer travelTimeShortfall(Long pilgrimageId, Long siteId) {
    Long previousSiteId = stampMapper.findLastCompletedSiteId(pilgrimageId).orElse(null);   // ← 대표
    ...
    int required = siteDistanceMapper.findMinMinutes(previousSiteId, siteId)            // ← (대표, 실제)
```

**왜 생겼나** — v4에서 `stamp.site_id` 컬럼을 추가하고 markGpsDone·markPending·toStatus 등은 다 고쳤는데 이 SELECT 하나를 빠뜨렸다. 주석은 v4 기준으로 갱신됐고 SQL은 v3 그대로다.

**실제 영향** — 1구 자리의 대표가 통도사, SUNROAD 후보가 서운암(차로 15분). 사용자가 서운암에서 인증 → 2구 자리로 이동 → 다짐 제출. 이동시간 검사는 (통도사 → 2구 사찰) 거리로 잰다. 서운암이 2구 쪽에 더 가까우면 정상 이동인데 보류로 빠지고, 더 멀면 부정 이동인데 통과한다. 단, 지금은 증상이 안 나타난다. 문제 ②로 이동시간 검사가 사실상 꺼져 있기 때문이다. ②를 켜기 전에 ①을 먼저 고쳐야 한다.

**해결** — `StampMapper.xml` `findLastCompletedSiteId` 구문 하나:
```xml
<!--
  직전 완료 도장의 "실제로 인증한" 사찰. v4 부터 stamp.site_id 가 실제 후보 사찰이다.
  COALESCE 는 v4 이전에 만들어져 site_id 가 NULL 인 옛 행을 위한 것이다 — 그 행은 대표 사찰로 잰다.
  ※ 이 값이 travelTimeShortfall 의 출발지가 된다. 도착지(stamp.getSiteId())와 기준을 맞춰야 한다.
-->
<select id="findLastCompletedSiteId" resultType="long">
    SELECT COALESCE(st.site_id, cs.site_id)
    FROM stamp st
             JOIN course_site cs ON cs.course_site_id = st.course_site_id
    WHERE st.pilgrimage_id = #{pilgrimageId}
      AND st.verify_status = 'COMPLETED'
      AND st.mission_verified_at IS NOT NULL
    ORDER BY st.mission_verified_at DESC
    LIMIT 1
</select>
```
바뀌는 건 `SELECT cs.site_id → SELECT COALESCE(st.site_id, cs.site_id)` 한 줄. 자바 코드·인터페이스·DTO 변경 없음.

**확인 방법** — `.\gradlew compileJava` · `.\gradlew bootRun`(Invalid bound statement 없이 뜨면 XML OK). 동작 확인:
```sql
SELECT st.stamp_id, st.pilgrimage_id, st.site_id AS actual, cs.site_id AS representative
FROM stamp st JOIN course_site cs ON cs.course_site_id = st.course_site_id
WHERE st.verify_status='COMPLETED' AND st.site_id <> cs.site_id
LIMIT 1;
```
그 pilgrimage_id로 다음 자리 다짐을 제출했을 때 로그의 "이동시간 미달로 보류. stampId=…, 부족분=…분"이 (actual → 다음) 쌍 기준이면 성공. JUnit: `.\gradlew test --tests "com.templestamp.stamp.*" --continue` 전부 통과(데모 코스는 대표=실제라 결과 불변).

### 1-3. 문제 ② 이동시간 검증이 실질적으로 꺼져 있다

**현상**
```yaml
stamp:
  default-travel-minutes: 0   # site_distance 에 없는 쌍은 검사하지 않는다
```
```java
int required = siteDistanceMapper.findMinMinutes(previousSiteId, siteId)
        .orElse(stampProperties.defaultTravelMinutes());   // 없으면 0
if (required <= 0) { return null; }   // ← 검사 안 함
```
`site_distance` 시드(data.sql 171행)는 데모 코스 site 1~5의 20행뿐. v4 시더(사찰 110곳·후보 215행)는 site_distance를 한 행도 넣지 않는다.

**실제 영향** — 실제 코스 12개에서 PENDING_TRAVEL_TIME 보류는 한 번도 발생하지 않는다. 두 절을 10분 만에 찍어도 통과다. 코드 버그가 아니라 데이터 미결. 인계문 §6-7 표(좌표 18곳·QR힌트 110곳·반경)에 이 항목이 빠져 있다.

**해결 — 두 갈래**

A. `default-travel-minutes`를 0보다 크게(즉시, 파일 1개): 예 `20`. 모든 쌍에 일괄 적용. 장점 즉시. 단점 인접 슬롯이 5분 거리인 경우 정상 사용자가 보류. 값은 파트너가 정한다.

B. `site_distance`를 코스 단위로 채운다(데이터 작업): 관리자 API `PUT /api/admin/site-distances`, 본문 `{"items":[{"siteAId":..,"siteBId":..,"minMinutes":..}]}`, 240행까지, UPSERT. 백엔드 수정 0. 현실적으로 대표 사찰끼리 20쌍 × 12코스 = 240쌍만 채우고 후보끼리는 A의 기본값 — A+B 병행.

C. 검사 범위(문제 ③) — 설계 결정: 두 쿼리 모두 `WHERE pilgrimage_id = #{pilgrimageId}`(같은 코스 안에서만). 하루 5개 한도는 사용자 전체로 세는데 이동시간은 코스별. 코스 5개에서 하나씩 찍으면 검사를 한 번도 안 받는다. **"사용자의 직전 완료 도장"**으로 바꾸면 코스를 넘나드는 순간이동도 잡힌다. 바꾼다면 WHERE를 `pilgrimage_id IN (SELECT pilgrimage_id FROM pilgrimage WHERE user_id = #{userId})`로, `travelTimeShortfall`이 userId를 받도록. 파일 2개(XML·Service). 파트너 결정 사항.

**확인(A 적용 시)** — 1구 gps-check→qr→mission 완료 직후 2구 3단계(5분 안에) → 200, `data.status="PENDING"`, 메시지 "이동하기에 이른 시간", 로그 "이동시간 미달로 보류 … 부족분=1X분". `SELECT stamp_id, verify_status, pending_reason FROM stamp WHERE stamp_id=?` → PENDING / TRAVEL_TIME.

## 2부. 사은품 / 보상

### 2-1. 구조 (근거 포함)

**정책 4종** — data.sql 302행 `reward_policy`:

| id | code | reward_type | trigger_type | 이름 | 수령 신청 |
|---|---|---|---|---|---|
| 1 | RW-STAMP | STAMP | STAMP_COMPLETED | 순례 도장 | ✗ |
| 2 | RW-COURSE | COUPON | COURSE_COMPLETED | 코스 완주 쿠폰 | ✗ |

### 2-2. 문제 ① 사용자 단위 보상이 순례 단위 키로 저장된다 — 실물 중복 위험

**현상(근거 3곳)**
1. 유니크 키 — `UNIQUE (reward_policy_id, stamp_id)`·`UNIQUE (reward_policy_id, pilgrimage_id)`. user_id가 어느 유니크에도 없다.
2. 적립 근거 — `CompletionService.completionRewards`에서 INTERIM·HOEHYANG 모두 `grantOrRestore(userId, policy, null, pilgrimageId)` — "방금 끝낸 코스"의 pilgrimage_id. "3번째로 완주한 코스가 무엇이냐"는 우연.
3. 회수 범위 — `revokeOrFlagForPilgrimage`: `WHERE pilgrimage_id = #{pilgrimageId} AND status='GRANTED'`. 어느 코스가 취소되느냐에 따라 같은 상황에서 다른 결과.

**재현(회향)** — ACTIVE 12, 하한 12. ① 12코스 완주, 마지막 P12 → (4,P12) GRANTED ② 신청·승인·발송 → PAID ③ 코스 3 반려 → cancelCourse(P3) → 완주 11 → (4,P12) PAID needs_review=1 ④ 재승인 → completeCourse(P3) → 완주 12 → `grantOrRestore(ALL_COMPLETED, null, P3)` → INSERT IGNORE (4,P3) 유니크 충돌 없음 → **삽입**. 결과 (4,P12) PAID + (4,P3) GRANTED → 신청 버튼 다시 켜짐. 기념품 2개.

**재현(중간본)** — P1·P2·P5 완주 → (3,P5). P1 취소 → 완주 2, INTERIM 그대로. P1 재승인 → 완주 3 → (3,P1) 추가. 중간본 2행.

`requeue_after_reject_does_not_duplicate_ebooks`는 전자책 중복 방지를 검증(enqueue가 `findAliveByUserAndType`으로 사용자+종류 단위) — 보상은 같은 테스트가 없다. 키 구조 차이.

**지금 당장 터지나** — 아니다. ACTIVE 1개라 도달 불가. 코스 12개 ACTIVE 전에 고쳐야 한다.

    <when test="stampId != null">AND ur.stamp_id = #{stampId}</when>

회수 대칭(⑤): cancelCourse가 회향은 회수하고 INTERIM은 안 하는 비대칭은 의도인지 확인 후 결정. 대칭이면 `if (countCompletedCourses(userId) < 3) revokeOrFlagByTrigger(userId, ON_THREE_COURSES_COMPLETED)`. 전자책은 안 건드린다. 제품 결정.

영향받는 테스트: `RewardServiceTest` 63·67·209행(grant 직접 호출은 그대로 통과) · `CompletionHardeningIntegrationTest.rewardCount` 영향 없음 · 새 테스트 `requeue_after_reject_does_not_duplicate_rewards` 권장.

확인: `SHOW CREATE TABLE user_reward\G` → user_key·uk_user_reward_user. 시나리오 후 (3,user) 1행·(4,user) 1행·pilgrimage_id NULL·user_key=user_id. 억지 중복 INSERT 두 번째 → ERROR 1062.

### 2-3. 문제 ② `completedCourses == 3` 등호 비교

`completeCourse`·`completionRewards` 두 곳. 정상 흐름(1→2→3)은 문제없으나 이미 4개 완주한 사용자에게 INTERIM 행이 없는 상태(①로 잘못 회수·데이터 보정)가 되면 다시는 못 받는다. 자기 치유가 안 된다. 문제 ①의 (policy,user) 유니크가 생기면 `>=`로 바꿔도 중복이 안 생기므로 `if (completedCourses >= INTERIM_COURSE_COUNT)`. 순서: ① 먼저. 확인: 완주 4인 사용자의 INTERIM 행을 지우고 5번째 완주 → 1행 생김, 6번째 → 여전히 1행.

## 3부. CORS

### 3-1. 현재 설정과 근거
```java
config.setAllowedOrigins(corsProperties.allowedOrigins());   // .env FRONTEND_URL + localhost:3000
config.setAllowedMethods(List.of("GET","POST","PUT","PATCH","DELETE","OPTIONS"));
config.setAllowedHeaders(List.of("Authorization","Content-Type","Accept-Language"));
config.setAllowCredentials(true);
source.registerCorsConfiguration("/**", config);
```
| 항목 | 왜 맞나 |
|---|---|
| allowCredentials(true) + 오리진 명시 | refresh 쿠키가 크로스 오리진으로 실리려면 필수. `*` 불가 |
| OPTIONS /** permitAll | preflight는 Authorization 없이 온다. 막히면 본 요청 시작 불가 |
| Accept-Language 허용 | 값 제한이 있어 명시가 안전. i18n 필수 |
| `@ConfigurationPropertiesScan` + record | CorsProperties 정상 등록, 콤마 → List |
| `.cors()`가 SecurityFilterChain 안에 | WebMvcConfigurer만 쓰면 시큐리티 필터가 먼저 401 → CORS 헤더 누락 사고를 피했다 |

### 3-2. 문제 ① X-Request-Id 허용·노출 누락
`RequestIdFilter`는 클라이언트 값을 받고 응답에도 싣는데 CORS에 둘 다 없다. 요청 방향: `Access-Control-Allow-Headers`에 없으면 브라우저가 본 요청을 안 보낸다. 응답 방향: `Access-Control-Expose-Headers`에 없으면 JS가 못 읽는다(기본 노출 6개뿐). RequestIdFilter javadoc의 목적("사용자 문의 → 로그 추적")을 이루려면 필수. 해결: `setAllowedHeaders`에 `X-Request-Id`, `setExposedHeaders(List.of("X-Request-Id"))`.

### 3-3. 문제 ② maxAge 미설정
CorsConfiguration 기본 null → 헤더 미전송 → 브라우저 기본 5초. POST/PATCH/DELETE·Authorization 붙는 GET마다 OPTIONS 추가. 인증 3단계 = OPTIONS 3번. 산속 LTE 왕복 수백 ms. `config.setMaxAge(3600L)`.

### 3-4. 문제 ③ 오리진 완전 일치 — Netlify 프리뷰
`setAllowedOrigins`는 완전 일치. Netlify 프리뷰(`deploy-preview-N--*.netlify.app`) 전부 차단. 필요하면 `setAllowedOriginPatterns(List.of("https://*.netlify.app"))`. 단 `_redirects`로 `/api/*`를 Render에 200 프록시하면 same-origin이라 CORS 자체가 없다 — 프록시 방식이면 무시. 지금은 건드리지 않기를 권한다.

### 3-5. 문제 ④ prod FRONTEND_URL 미설정 시 조용히 전부 차단
`application-prod.yml`의 `cors.allowed-origins: ${FRONTEND_URL}` — `RequiredEnvCheck.PROD_REQUIRED`에 FRONTEND_URL이 없다. 미설정이면 문자열 "${FRONTEND_URL}"로 기동 성공, 모든 브라우저 요청 차단(Postman은 됨). `PROD_REQUIRED.put("FRONTEND_URL", "운영 환경변수");` 한 줄.

### 3-6. 해결 코드 — SecurityConfig.corsConfigurationSource()
```java
@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(corsProperties.allowedOrigins());
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
    config.setAllowedHeaders(List.of(
            "Authorization", "Content-Type", "Accept-Language",
            RequestIdFilter.HEADER));                       // ★ 요청 헤더 허용
    config.setExposedHeaders(List.of(RequestIdFilter.HEADER)); // ★ 응답 헤더 노출
    config.setAllowCredentials(true);
    config.setMaxAge(3600L);                                // ★ preflight 1시간 캐시
    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", config);
    return source;
}
```
바뀐 줄: import 1(RequestIdFilter) · allowedHeaders에 상수 1 · exposedHeaders 1 · maxAge 1. 나머지 동일. 주의: config→web 방향 의존이 생긴다(싫으면 문자열 "X-Request-Id" 직접). `RequiredEnvCheck`의 FRONTEND_URL 한 줄은 별도 파일.

**확인** — `.\gradlew bootRun` ERROR 0. preflight:
```
OPTIONS http://localhost:8080/api/stamps/1/gps-check
Origin: http://localhost:5173
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization,content-type,x-request-id
```
예상: 200 · Allow-Origin localhost:5173 · Allow-Headers에 x-request-id · Expose-Headers X-Request-Id · Allow-Credentials true · Max-Age 3600. `Origin: http://evil.com` → 403. 브라우저: 같은 API 재호출 시 OPTIONS가 안 뜨면 maxAge 캐시 작동.
