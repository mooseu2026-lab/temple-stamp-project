### 사찰 시드는 어디서 오나 — **CSV 를 읽는 시더 클래스**

`data.sql` 에 `INSERT INTO site` 는 **0건**이다(데모 5곳은 다른 문장으로 들어간다).
시드는 `SiteSeedImporter` 가 CSV 두 개를 읽어 **관리자 서비스를 호출해** 만든다.

```java
// SiteSeedImporter.run — --spring.profiles.active=local,seed 로 기동하면 한 번 돌고 끝난다
List<Map<String, String>> sites = SeedCsv.read("seed/sites-master.csv");     // 111행
List<Map<String, String>> slots = SeedCsv.read("seed/slot-candidates.csv");
...
var req = new AdminSiteSaveRequest(ll[0], ll[1], DEFAULT_RADIUS, null,
        r.get("parking_info"), r.get("access_info"), r.get("meal_available"), i18n);
siteId = adminSiteService.create(req).siteId();
siteMapper.updateSeedKey(siteId, key);
```

**그래서 STEP 3 의 반영 방식은 "CSV 병합" 이다.** `data.sql` 에 UPDATE 블록을 붙이면
빈 DB 에서 시더가 만든 값을 나중에 덮어쓰는 두 겹 구조가 되고, 둘이 어긋나는 날이 온다.

시더의 성질 둘을 기억해야 한다.

- **멱등하되 갱신하지 않는다.** `siteId == null` 일 때만 만든다. 이미 있는 사찰의 주차·공양은 **다시 쓰지 않는다** →
  기존 DB 에는 시더를 다시 돌려도 보강이 반영되지 않는다. 그래서 STEP 4 가 따로 있다.
- **`seed_key = REGION:이름:구분`** 이 멱등의 축이다. 이름을 바꾸면 키가 바뀌고, 키가 바뀌면 **같은 절이 하나 더 생긴다.**

### 공양 — 서술 12종을 값 4종으로

원본은 자유 문자열이었다.

```
43 미확인 · 41 사찰음식·템플스테이 · 15 사찰음식 · 2 사찰음식·템플스테이(외국인 특화)

```

| 값 | 뜻 | 규칙 |
|---|---|---|
| `TEMPLE_MEAL` | 절에서 사찰음식을 낸다(템플스테이 포함) | "사찰음식" 또는 "템플스테이" 가 있으면 |
| `PUBLIC_MEAL` | 대중공양·공양간 | "공양간"·"대중공양" |
| `NEARBY` | 절 밖 인근 식당 | "인근"·"주변 식당" |
| `NONE` | 공양 없음 | "없음"·"불가" |
| (빈칸) | **아직 모른다** | "미확인"·빈칸 |

> **"미확인" 을 `NONE` 으로 접지 않았다.** "없다" 와 "모른다" 는 다른 사실이다.
> `NONE` 을 넣으면 확인해 보지도 않고 "공양 없음" 이 화면에 나간다.
> 이 구분 때문에 `schema.sql` 주석에도 "NULL 은 없다가 아니라 아직 모른다" 를 적어 두었다.

### 2026-09-08 정정 — "미확인" 도 공양이 있다

위 표는 **조사 자료만** 보고 매긴 것이다. 그 뒤 예성이 확인해 주었다 —
**대부분의 절에 공양이 있다. 다만 시간이 정해져 있고 사전에 연락을 해야 한다.**

그래서 판정을 바꿨다.

| | 바꾸기 전 | 바꾼 뒤 |
|---|---|---|
| "미확인" | 빈칸(모른다) | **`TEMPLE_MEAL`** |
| 비공식 등급 행 | 값을 비움 | **등급을 가리지 않는다** |
| 개발 DB | `TEMPLE_MEAL` 49 · 빈칸 65 | **`TEMPLE_MEAL` 114 · `PUBLIC_MEAL` 1** |

"모른다" 를 `NONE`(없다) 으로 접지 않은 판단은 그대로 옳았다 — 다만 **빈칸으로 두는 것도 틀렸다.**
있는 것을 모른다고 표시하면 화면에 "공양 정보 없음" 이 뜨고, 그것도 사실과 다르다.

**시간·사전 연락 조건은 `meal_available` 에 담기지 않는다.** 값 4종은 "있다 / 없다 / 어디서" 만
말하고, 시간은 절마다 다르며 아직 조사되지 않았다. 그 조건은 **화면 공통 안내**로 나간다 —
`frontend-handoff.md` §공양 에 문구까지 못 박아 두었다. 절별 시간이 확인되면 그때 사찰별 안내로 바꾼다.

조사 자료에 **`PUBLIC_MEAL`·`NEARBY`·`NONE` 에 해당하는 절은 하나도 없었다.**
값 넷 중 둘은 이번 반영에서 쓰이지 않는다 — 그래도 체계는 넷으로 둔다(나중에 조사가 오면 자리가 있어야 한다).

### 🚨 고운사 대표 교체가 막혔다 — 코스 자리 수정 자체가 불가능하다

§0-2 는 "코스에 이미 배정돼 있으면 후보 사찰로 대체" 를 요구한다.
고운사는 **대구/경북 공양의 길(course 39) 3번 자리의 대표**이고, 같은 자리에 후보로 **희방사**가 있다.
빈 DB 는 `slot-candidates.csv` 에서 고운사를 빼서 희방사가 자동으로 대표가 되었다.
개발 DB 는 관리자 API 로 바꿔야 하는데 — **500 이 났다.**

```
PUT /api/admin/courses/39   자리 1:990405 2:990407 3:990411(희방사) 4:990412 5:990414
→ 500 COMMON-5000

Caused by: SQLIntegrityConstraintViolationException: Cannot delete or update a parent row:
  a foreign key constraint fails (`slot_site`, CONSTRAINT `fk_slot_site_course_site_id`
  FOREIGN KEY (`course_site_id`) REFERENCES `course_site` (`course_site_id`) ON DELETE RESTRICT)
```

`courseService.save` 가 자리를 바꿀 때 `course_site` 행을 **지우고 다시 넣는다.**
v4 에서 `slot_site` 가 생기면서 그 행들이 `course_site_id` 를 `RESTRICT` 로 잡게 됐고,
**후보가 하나라도 붙은 코스는 자리를 영영 바꿀 수 없다.** 지금은 모든 코스에 후보가 붙어 있다.

겹치는 문제가 둘이다.

1. **기능** — 관리자 코스 자리 수정이 사실상 죽어 있다.
   `정리.md` §3 의 "관리자 콘텐츠 저장은 UPSERT 만 · 삭제 후 재삽입 금지" 를 이 경로가 어기고 있다.
2. **오류 처리** — FK 위반이 `COMMON-5000` 으로 새어 나간다. 관리자에게 왜 막혔는지가 전달되지 않는다.

**이번 회차에서는 고치지 않았다** — C1 은 ErrorCode·엔드포인트 신설이 없는 회차이고,
이 수정은 `courseService.save` 의 저장 방식을 UPSERT 로 바꾸는 일이라 범위가 다르다.

**당장의 위험은 없다.** 코스를 ACTIVE 로 올리려면 자리 5곳이 전부 ACTIVE 여야 하는데
(`AdminCourseService.changeStatus` → `ADMIN-4092`), 고운사가 INACTIVE 라 **그 코스는 어차피 열리지 않는다.**
11-A STEP 6 에서 이 코스가 실패로 잡힐 것이고, 그 자리에서 함께 고치는 것이 맞다.

> `PUT /api/admin/sites/{id}` 는 **전체 교체**다. 보내지 않은 칸은 지워진다.
> 그래서 도구가 지금 값을 먼저 읽어 합친 뒤 보낸다(`coord-backfill.js` 와 같은 수법).
> 이 성질을 모르고 부분만 보내면 주차 안내가 통째로 사라진다.

### 🚨 부하 시험에서 5xx 18건 — 교착이 아니라 커넥션 풀 고갈
