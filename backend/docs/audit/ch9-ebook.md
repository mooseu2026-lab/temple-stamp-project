# 챕터 9 — 전자책 · 인증서 PDF · 인쇄주문 · 청소기 (구현 기록)

정본: `backend/docs/textbook/ch9.md` · 교체·삭제한 원본: `backend/docs/audit/ch9-replaced/`
스키마 변경: `backend/docs/verify/alter-ch9.sql` (정리.md §5-1 ⑮⑯⑰) · 마지막 코드 챕터

이 챕터가 한 일은 **글자를 파일로 바꾸는 것**이다. 지금까지 사용자의 기록은 API 응답으로만
존재했고, 손에 쥘 수 있는 것이 없었다. 이제 PDF 한 권과 인증서 한 장이 나오고,
그것을 종이로 찍어 보내는 길과, 지워야 할 파일을 실제로 지우는 청소기가 생겼다.

---

## 0. 시작하자마자 드러난 것 — 저장소에는 파일이 없었다

`ObjectStorageClient` 는 **서명만 만들고 바이트를 저장하지 않았다.** `presignGet` 이 가리키는
`http://localhost:9000` 에는 아무 서버도 없다. 챕터 6 의 사진도 실제로는 키만 기록됐다.

PDF 를 만들려면 바이트를 둘 곳이 있어야 하고, 청소기가 지울 것도 있어야 한다.
그래서 `provider=local` 일 때 **디렉터리에 실제로 쓰는** 네 메서드(`put`·`getBytes`·`exists`·`delete`)를
그 클래스에 붙였다. 의존성은 늘리지 않았고, S3 로 갈아 끼울 때 이 네 개만 SDK 호출로 바꾸면 된다.

그 대가로 **E06(다운로드 URL 을 열어 `%PDF` 확인)을 newman 으로 측정할 수 없다.**
로컬에 S3 대역이 없기 때문이다. 서명을 받아 주는 문을 하나 만드는 길은 §7 의 다섯 개 상한과
"서버는 PDF 를 직접 스트리밍하지 않는다" 에 걸린다. 그래서 이렇게 나눴다 —

| 무엇을 | 어디서 |
|---|---|
| 서명 URL 의 모양(버킷·키·만료·서명) | newman E06 |
| 파일이 `%PDF` 로 시작하는가 · 한글이 들어 있는가 | JUnit `EbookServiceTest ⑦` (저장소에서 직접 읽는다) |

## 1. 대조 — 있던 것과 바꾼 것 (§0·§2-1·§4)

세 표(`ebook`·`print_order`·`storage_orphan`)가 **전부 0행**이었다. 그래서 컬럼을 지우고
CHECK 를 좁히는 쪽을 골랐다 — 옮길 데이터가 없다. 행이 있었다면 옛 값을 CHECK 에 남기고
UPDATE 로 옮겼을 것이다.

| 대상 | 저장소에 있던 것 | 정본 | 판정 |
|---|---|---|---|
| `ebook.status` | `QUEUED→BUILDING→READY/FAILED` | `REQUESTED→READY/FAILED` | **교체**. `BUILDING` 을 없앴다 — §2 참조 |
| `ebook.pdf_key`·`queued_at`·`built_at` | 있음 | `file_key`·`requested_at`·`ready_at` | **유지**(이름만 다르다). EPUB 은 범위 밖이라 `epub_key` 도 그대로 |
| `snapshot_hash`·`page_count`·`byte_size` | 없음 | 필요 | **추가** + `(user_id, snapshot_hash)` 유니크 |
| `ebook_type` | PILGRIMAGE/INTERIM/HOEHYANG | 개인 소장본 | **확장** — `PERSONAL` |
| `ebook.retry_count`·`building_started_at` | 있음 | 없음 | **유지하되 쓰지 않는다**(옛 대기열 잔재) |
| `print_order` 상태 | REQUESTED/CONFIRMED/SHIPPED/CANCELED | +PRINTING·DONE | **확장**(이름 유지, 없는 것만 추가) |
| 배송정보 다섯 칸 | `print_order` 본체 | `print_order_address` | **교체** — §4 참조 |
| `quantity` 1~3 | | 1~5 | **확장** |
| `cancel_reason`·`needs_review` | 없음 | 필요 | **추가** |
| `storage_orphan` | 표만 있고 소비자 없음 | 큐 | **확장** — `status`·`retry_count`·`needs_review`·`last_error` |
| 인쇄 자격 "회향본만" | `isHoehyang()` | "본인 READY 전자책만" | **교체**. 개인 소장본이 인쇄 대상이 되면서 옛 제한이 뜻을 잃었다 |
| 스케줄러 | 도장 만료(5분)·토큰 정리(하루) 둘 | 청소기 하나 | **통합** — §5 참조 |

### 스택 추가 1건

**OpenPDF 2.0.3**(LGPL/MPL). 저장소에 다른 PDF 라이브러리는 없었다.
한글 폰트 `src/main/resources/fonts/NotoSansKR-Regular.ttf`(OFL, 6.1 MB)를 함께 넣었다 —
정본은 `.otf` 로 적었지만 구글 폰트가 배포하는 것은 `.ttf` 이고 라이선스와 글리프는 같다.
**6 MB 가 jar 에 들어간다**는 점은 배포 전에 알고 있어야 한다(정리.md §5).

## 2. 전자책 (§2)

### 축은 스냅샷 해시 하나다

```
재료 = 도장 id · 사진 키 · 원고 id · 문장 길이 · 생각상자 id · 인증서 번호 · 명상 횟수·시간
해시 = 그것을 정렬해 SHA-256
같은 해시 → 같은 책 (새로 만들지 않고 있던 것을 준다)
```

**본문 글자가 아니라 id 로 해싱하는 이유**가 있다. 도장에 붙은 원고가 나중에 퇴역해도
그 도장이 붙든 원고 id 는 그대로다(챕터 8 §3-2). 내용으로 해싱하면 원고를 한 번 고칠 때
모든 사람의 책이 "새 책" 이 되어 다시 만들어진다.

### 상태를 셋으로 줄였다

`REQUESTED → READY / FAILED`. `BUILDING` 을 없앤 것이 이 챕터의 판단이다.
있는 행을 `FOR UPDATE` 로 잠그고 그 트랜잭션 안에서 만들면 중간 상태가 필요 없고,
중간 상태는 **"BUILDING 인 채 죽은 행"** 을 회수하는 코드를 또 부른다.
잠금은 챕터 8 의 규칙 그대로 **있는 행에만** 건다.

### 상한 둘, 그리고 그 상한이 세지 않는 것

| 상한 | 값 | 코드 |
|---|---|---|
| 만드는 중 | 사용자당 1권 | 409 `EBOOK-4092` |
| 하루 생성 | 3권(설정) | 429 `EBOOK-4290` |
| 남겨 두는 권수 | 5권(설정) | 넘으면 최고령 삭제 + 파일 키는 큐로 |

두 상한은 **개인 소장본만 센다.** 완주가 만들어 주는 코스본까지 세면 **완주한 날에는
개인 소장본을 만들 수 없다** — 가장 만들고 싶은 날인데 막히는 셈이다. 상한의 목적은
사용자가 버튼을 연달아 누르는 것을 막는 것이지 시스템이 만든 책이 아니다.
(이 결함은 폴더 E 를 돌리다 429 가 떠서 드러났다.)

권수 정리에서 **인쇄 주문이 걸린 책은 빠진다**(함정 7). 종이로 찍는 중인 책을 지우면
주문서가 가리키는 것이 사라진다.

### 페이지와 사진

표지 · 걸어온 길 · 도장(한 장마다 1쪽) · 생각상자 · 명상 · 인증서 · 판권.
생각상자는 **비공개도 들어간다** — 개인 소장본이라 남에게 나가지 않는다.
사진은 긴 변 1200px·JPEG 80 으로 줄여 넣는다(함정 2). 저장소에 사진이 없으면
"사진 없음" 을 적고 넘어간다 — **한 장이 없다고 책 한 권이 실패하면 안 된다.**

## 3. 인증서 PDF (§3)

`GET /api/certificates/{id}` — 본인 1장. **VALID 일 때만** 링크가 붙고 REVOKED 면 `null` 이다
(에러가 아니다 — 회수됐다는 사실도 답이다).

PDF 는 **첫 조회 때** 만든다. 발행 시점에 만들면 아무도 내려받지 않는 파일까지 전부 만들어 두게 되고
그중 상당수는 회수돼 버려진다. 키를 적는 자리(`CertificateMapper.updateFileKey`)는
챕터 7 부터 비워 둔 것이고 여기서 처음 쓰였다.

증서에는 **이름이 통째로** 찍힌다 — 본인만 받는 파일이다. 공개 진위 확인의 마스킹과 목적이 다르다.

**파일이 정본이 아니라 QR 이 가리키는 곳이 정본이다.** 한 번 내려받은 파일은 누군가의
컴퓨터에 남고 회수해도 사라지지 않는다. 그래서 회수 시 파일을 지우지 않고 링크만 끊는다 —
QR 을 찍으면 진위 확인이 `REVOKED` 를 답한다(함정 8).
JUnit 이 그 QR 을 **디코드해서** 주소가 맞는지 본다("그렸다" 가 아니라 "읽힌다" 를 봐야 한다).

## 4. 인쇄주문 (§4)

```
REQUESTED ─확인─▶ CONFIRMED ─인쇄중─▶ PRINTING ─발송─▶ SHIPPED ─완료─▶ DONE
    │                  │
    │                  └─관리자 취소(사유 필수)─▶ CANCELED
    └─사용자 취소(DELETE 204)─▶ CANCELED        ※ REQUESTED 에서만
```

**PRINTING 부터는 취소가 없다.** 종이가 이미 나가고 있어 되돌릴 수 없다.
전이는 코드가 아니라 **UPDATE 의 WHERE 절**에 넣는다 — 먼저 읽고 나중에 쓰면
두 관리자가 같은 주문을 동시에 옮길 때 둘 다 성공한다. 영향 행 수 0 = 허용되지 않은 전이다.

표 밖의 전이는 전부 같은 답 409 `PRINT-4090` 이다. 다만 **중복 신청은 `PRINT-4091`** 로 갈랐다 —
둘 다 409 지만 사용자가 할 일이 다르다. 하나는 기다리는 것이고 하나는 다른 책을 고르는 것이다.

배송정보는 `print_order_address` 로 뗐다. 목록 질의가 그 표를 **조인하지 않으므로**
목록으로 주소가 새어 나갈 길이 애초에 없다 — 응답에서 지우는 방식은 필드가 하나 늘 때
지우는 것을 잊으면 그대로 나간다. 관리자 목록에는 실린다(실제로 보내야 하는 사람이다 · 보상과 같은 원칙).

그 결과 `PrintOrderResponse.maskPhone/maskAddress` 가 쓰이지 않게 됐다.
**마스킹을 없앤 것이 아니라 마스킹할 대상이 사라졌다** — `MaskingTest` 는 이제
"목록 응답에 주소 계열 칸이 아예 없다" 를 못 박는다.

## 5. 청소기 (§5) — 스케줄러를 하나로 모았다

5분마다 도는 스케줄러 하나가 네 가지 일을 한다.

| 작업 | 규칙 | 한 번에 |
|---|---|---|
| ① 파일 삭제 큐 | 실패 5회 초과 → `FAILED` + `needs_review`. **저장소에 이미 없는 키는 성공** | 100건 |
| ② 만료 토큰 | **만료 시각 + 24시간**이 지난 것만. 폐기됐어도 미만료면 남긴다 | 1,000건 |
| ③ 전자책 조판 | REQUESTED 를 오래된 것부터 | 3권 |
| ④ 도장 세션 만료 | 챕터 5 의 5분 청소기를 여기로 통합 | — |

**작업마다 트랜잭션이 따로다.** 저장소가 잠깐 아프다는 이유로 도장 세션이 영원히 열려 있으면
안 된다(함정 10). 실행마다 로그 한 줄이 나가고, 관리자 수동 실행
`POST /api/admin/housekeeping/run` 이 **같은 숫자**를 응답으로 준다 —
5분을 기다리는 것 말고 다른 길이 있어야 한다.

② 의 기준이 "폐기" 가 아니라 "만료 + 유예" 인 것이 요점이다. 폐기된 토큰을 지우면
챕터 1 의 재사용 탐지가 눈을 잃는다 — 이미 쓴 토큰이 또 왔을 때 그 행이 있어야
"재사용" 이라고 말할 수 있고, 지워 버리면 그냥 "모르는 토큰" 이 된다(함정 6).

기존 `AuthService.cleanUpExpiredTokens`(하루 한 번)를 여기로 옮겼다.
그것은 **실제로는 한 번도 지운 적이 없었다** — 토큰 수명이 그 주기보다 길다.
점검 E 가 사용자 8명에 1,674행을 실측한 것이 그 결과다.

## 6. 관리자 사용자 목록 (§6)

`GET /api/admin/users?status=&q=&page=&size=` — 기본 `ACTIVE`, `?status=DELETED` 를
**명시할 때만** 탈퇴 계정. 비밀번호 해시는 **질의가 읽지 않는다**(응답 DTO 에서 빼는 방식이 아니다).

정본이 적은 "마지막 로그인" 은 **없다** — 저장소에 그 칸이 없고, 매 로그인마다 `users` 를 쓰는
비용이 붙는 일이라 이 챕터에서 만들지 않았다. 필요해지면 별도 표가 맞다(§15 [질문]).

## 7. 탈퇴 연쇄 보강 (§2-5) — 실측에서 500 이 났던 자리

정본은 "ebook 행 삭제 + 파일 키 큐로 / print_order REQUESTED→CANCELED, 그 이후는 needs_review"
라고 적었다. 그대로 짰더니 **FK 로 막혀 500** 이 났다 — 남겨 둔 주문이 지우려는 전자책을 붙들고 있었다.

정리한 규칙은 이렇다.

| 상태 | 주문 | 전자책 |
|---|---|---|
| REQUESTED | 취소한 뒤 **행까지 지운다** | 함께 지운다 + 파일 키는 큐로 |
| CONFIRMED 이후 | 취소하지 않고 `needs_review` | **남긴다** — 주문서가 가리키는 것이 사라지면 안 된다 |

끝난 주문을 남겨 두면 탈퇴한 사람의 PDF 가 저장소에 그대로 남는다. 그래서 지운다.
진행 중인 주문은 인쇄소가 이미 들고 있어, 시스템이 취소해도 그 일이 되돌아오지 않는다.
배송정보는 어느 쪽이든 지운다 — 개인정보이고, 남은 주문은 관리자가 이미 받아 적었다.
**순서는 주문이 먼저, 전자책이 나중이다.**

## 8. 엔드포인트 다섯 신설 — 86 → 91

| # | 문 | 인증 | 비고 |
|---|---|---|---|
| 1 | `POST /api/ebooks` | USER | 202 REQUESTED · 같은 재료면 200 |
| 2 | `GET /api/ebooks/{id}` | USER | `downloadUrl` 은 READY 일 때만 |
| 3 | `GET /api/certificates/{id}` | USER | 챕터 7 이월 · 첫 조회에 PDF 생성 |
| 4 | `GET /api/admin/users` | ADMIN | §6 |
| 5 | `POST /api/admin/housekeeping/run` | ADMIN | §5 |

`GET /api/ebooks` 는 이미 있어 신설이 아니다. 기존 인쇄주문 4 + 관리자 5 는 §4 로 대조했고,
**미검증 2건(`GET`·`DELETE /api/print-orders/{id}`)이 닫혔다** — 엔드포인트 ⚠ 가 0이 됐다.

`DELETE /api/print-orders/{id}` 는 200 에서 **204** 로 바꿨다(§4-1). 남길 말이 없는 응답에
빈 봉투를 실을 이유가 없다 — 탈퇴와 같은 판단이다.

## 9. 오류코드 (§5 대조)

명세 대조 결과 **넷이 없어 구현 누락으로 추가**했다. 번호와 생성자 순서는 건드리지 않았다.

| 코드 | 뜻 |
|---|---|
| `EBOOK-4001` | 기록이 없어 전자책을 만들 수 없습니다 (400) |
| `EBOOK-4092` | 만드는 중인 전자책이 있습니다 (409) |
| `EBOOK-4290` | 하루에 만들 수 있는 수를 넘었습니다 (429) |
| `PRINT-4001` | 만들어진 전자책만 인쇄할 수 있습니다 (400) |

옛 `verify-ch0-5.md` 가 `EBOOK-4092` 를 "파일 없음" 으로 적어 두었으나 코드에는 없었고,
정본(§2-2)이 그 번호를 "동시 요청 상한" 으로 쓴다 — **정본이 이긴다.**

`PRINT-4090`·`PRINT-4091` 은 역할이 갈리면서 **기본 메시지만** 고쳤다(번호는 그대로).

## 15. [질문]

| # | 항목 | 현재 | 권고 |
|---|---|---|---|
| 1 | 결제 연동 | 없다. `print_price` 는 설정값이고 "관리자 확인 = 입금 확인" 이다 | 결제가 붙으면 CONFIRMED 앞에 PAID 가 하나 더 필요하다. 그때 상태 기계를 다시 본다 |
| 2 | 다중 인스턴스 | 청소기는 **단일 인스턴스 전제**다. 전자책은 있는 행 잠금으로 막지만 나머지는 중복 실행이 무해할 뿐 막혀 있지 않다 | 인스턴스를 늘리기 전에 ShedLock. 지금 넣으면 쓰지 않는 표가 하나 는다 |
| 3 | 폰트 6 MB | jar 에 그대로 들어간다 | 배포 크기가 문제되면 필요한 글리프만 추린 서브셋. 지금은 그대로가 안전하다 |
| 4 | 마지막 로그인 | 칸이 없다 | 별도 표(`login_history`)가 맞다. `users` 에 칸을 더하면 로그인마다 그 행을 쓴다 |
| 5 | 저장소 실물 | `provider=local` 은 디렉터리에 쓴다 | 운영은 S3. `ObjectStorageClient` 의 네 메서드만 바꾸면 되고 호출부는 그대로다 |
| 6 | 탈퇴 유예 기간 | 없다(즉시 익명화) | 챕터 1 보강부터 열려 있는 제품 결정. 유예를 두면 상태가 하나 더 필요하다 |
