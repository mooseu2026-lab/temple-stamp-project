## 1. 판정표 — 정본 §3 아홉 단계

| 순서 | 대상 | 정본 | 저장소는 어땠나 | 한 일 |
|---|---|---|---|---|
| 1 | user | 익명화 + `status=DELETED`·`deleted_at` | 컬럼 자체가 없었다 | **신규** — `status`·`deleted_at` 추가, `password` 를 NULL 허용으로. 이메일은 `deleted-{id}@invalid`, 닉네임은 `탈퇴회원`, 계층(연령대)은 NULL |
| 2 | refresh·세션 | 전부 무효 | `revokeAllByUser` 가 이미 있다 | 재사용 — 챕터 1 의 재사용 탐지와 같은 경로 |
| 3 | 동의 기록 | 유지 + 철회 시각 | `withdrawByType`(한 종류)만 있었다 | **신규** `withdrawAll` — 행은 남기고 시각만 |
| 4 | 진행 중 도장 세션 | `EXPIRED` | 사용자 단위로 닫는 길이 없었다 | **신규** `expireOpenByUser` — `GPS_DONE·QR_DONE·PENDING` 만. `COMPLETED` 는 완주의 근거라 손대지 않는다 |
| 5 | 인증서 VALID | `REVOKED`(`USER_WITHDRAWN`), verify 는 200+REVOKED, 이름은 `탈퇴회원` | 사유 상수도 없었다 | **신규** `revokeAllByUser` + `Certificate.USER_WITHDRAWN`. 공개 응답은 `holderStatus` 를 보고 마스킹 대신 `탈퇴회원` 을 낸다 |
| 6 | 보상 | GRANTED→REVOKED, 나머지 `needs_review` | 완주 취소용(`ByPilgrimage`)만 있었다 | **신규** `revokeGrantedByUser`·`flagNeedsReviewByUser` — 챕터 7 §2-4 와 같은 규칙 |
| 7 | `reward_claim` | 행 삭제 | 없었다 | **신규** `deleteByUser` |
| 8 | 사진·문장·생각상자·명상 | 행 삭제 + 사진 키를 `storage_orphan` 큐로 | 표도 없었다 | **신규** `storage_orphan` 표 + `deleteByUser` 셋 |
| 9 | 완주 기록 | 유지 | — | 손대지 않았다(집계용, 개인정보 없음) |

**아홉이 한 트랜잭션이다.** 중간에서 멈추면 "인증서는 회수됐는데 계정은 살아 있는" 상태가 남고 그것은 아무도 못 고친다 — JUnit 이 그 롤백을 실측한다.

### 순서를 왜 그렇게 두었나

세션을 **맨 먼저** 끊는다. 뒤 단계가 도는 동안 그 토큰으로 무언가 더 만들 수 있으면 안 된다.
사람(`users`)은 **맨 마지막**에 익명화한다. 앞 단계들이 `user_id` 로 찾아 들어가기 때문이다.

### 저장소 파일을 트랜잭션 안에서 지우지 않는 이유

저장소 호출이 실패하면 탈퇴 전체가 롤백된다. **"지워 달라" 는 요청이 저장소가 잠깐 아프다는 이유로
아무 일도 일으키지 못하는 것이 가장 나쁘다.** 그래서 DB 에는 지금 적고(`storage_orphan`), 파일은 챕터 9 청소기가 지운다.

## 2. 엔드포인트 — `DELETE /api/users/me` (77번째)

```
DELETE /api/users/me   USER   body { "password": "…" }   →  204 (본문 없음)
```

- **비밀번호를 다시 받는다.** 되돌릴 수 없는 일이고, 세션이 살아 있다는 것만으로는 근거가 되지 않는다
  (자리를 비운 사이 남이 누를 수 있다). 틀리면 로그인과 **같은 코드(`AUTH-4011`)·같은 5회 잠금**이다 —
  규칙을 새로 쓰지 않고 `AuthService.reauthenticate` 가 login 과 같은 매퍼를 쓴다.
- 서비스 메서드는 `deleteAccount` 다. 기존 `withdraw`(약관 철회)와 이름을 나눴다 — 하나는 되돌릴 수 있고 하나는 없다.
- **`@Transactional(propagation = NOT_SUPPORTED)`** 가 붙어 있다. `UserService` 는 클래스에
  `@Transactional(readOnly = true)` 가 걸려 있어서, 그냥 두면 읽기 전용 트랜잭션이 바깥에 열리고
  안쪽 쓰기가 `Connection is read-only` 로 죽는다(실제로 5xx 를 한 번 봤다). 여기서는 트랜잭션을 열지 않고
  재확인과 연쇄가 **각자** 자기 트랜잭션을 연다 — 그래야 실패 횟수 UPDATE 가 예외에 휩쓸리지 않는다(§6-2).

### 액세스 토큰을 즉시 막는 방법

액세스 토큰은 무상태라 "폐기" 라는 것이 없다. 30분을 그냥 두면 탈퇴한 사람이 그동안 계속 쓴다.
그래서 **JWT 필터가 매 요청 `users.status` 를 한 번 읽는다**(기본키 조회). `DELETED` 면 컨텍스트를 비우고
그대로 통과시켜 `EntryPoint` 가 401 `AUTH-4013` 을 쓴다.

- 다른 방법은 둘 다 더 비싸다 — 블랙리스트는 저장소를 하나 더 늘리고, 만료를 짧게 잡으면 모든 사용자가 자주 다시 로그인해야 한다.
- 비용은 인증된 요청당 기본키 읽기 하나다. 이 앱의 거의 모든 엔드포인트는 이미 DB 를 친다.

## 6. 이번에 겪은 것 둘

1. **읽기 전용 트랜잭션에 갇혔다.** `UserService` 클래스의 `@Transactional(readOnly = true)` 때문에
   탈퇴가 `Connection is read-only` 로 500 을 냈다. 클래스 기본값이 메서드에 그대로 내려온다는 것을
   잊으면 "쓰기만 하는 메서드" 가 조용히 못 쓰게 된다. → `NOT_SUPPORTED`.
2. **한글을 argv 로 넘겨 본문이 깨졌다.** 손으로 확인하려고 `curl -d '{"nickname":"탈퇴시험"}'` 를 썼다가
   `COMMON-4004` 를 받았다 — 정리.md §2 에 이미 적혀 있는 함정을 내가 다시 밟았다. `--data-binary @파일` 로 바꿨다.

도구도 한 번 일했다: 새 컬럼(`status`·`deleted_at`)을 `User` 조회 SQL 에 넣지 않아
`mapper-check.js` 가 **"별칭 미채움 2건"** 으로 잡았다. 안 잡혔으면 필드가 조용히 null 인 채로 남았을 것이다.
