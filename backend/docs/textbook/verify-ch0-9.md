## 3. 배포에서만 드러나는 항목 (이번 점검의 본론)

### 3-1 빈 DB 재구축 (가장 중요)
1. 새 스키마 `temple_stamp_verify_f` 생성(빈 상태)
2. `schema.sql`만으로 표 전부 생성 — **alter-ch7~9.sql은 쓰지 않는다**(schema.sql이 ALTER 17건을 전부 흡수했는지 검증)
3. 시더 실행 → 시드 숫자(사찰 110·코스 12 DRAFT·자리 60·후보 213·요소 342·region 10·원고 10·편집자 1·보상 규칙 4·cert_serial 2)
4. 이 DB로 `bootRun` → 헬스 → run-all.sh 2회 동일
5. 기존 개발 DB와 `information_schema` 전수 비교(표·컬럼·인덱스·유니크·FK·생성 컬럼) → **차이 0**
6. 끝나면 verify_f 스키마 삭제

차이가 하나라도 있으면 그것이 배포 첫 기동을 막을 결함이다.

### 3-2 저장소 실재
- 사진 업로드 → 저장소에서 바이트 읽기 → JPEG/PNG 헤더 확인 → 사이즈 > 0
- 전자책 READY → 바이트 읽기 → `%PDF` → 텍스트 추출에 한글·사찰명·인증서 번호 포함
- 인증서 PDF → `%PDF` → QR 디코드(zxing) = `{public-base-url}/verify/{번호}`
- orphan 처리 후 → 그 키 읽기 실패(정말 지워졌는가)
- presigned URL 만료(10분) 뒤 401/403 — 만료 시각을 짧게 바꾼 테스트 프로파일로 실측

### 3-3 prod 프로파일 드라이런
`SPRING_PROFILES_ACTIVE=prod`로 **로컬에서** 기동(시크릿은 더미 env). 확인:

| 항목 | 기대 |
|---|---|
| 시크릿 | JWT·DB·저장소·카카오·public-base-url이 env에서만 읽힘. 코드·yml에 값 없음(grep) |
| DDL | `spring.sql.init.mode=never`, 시더는 prod에서 **명시 플래그 없이는 안 돎** |
| 로그 | 레벨 INFO, SQL 로그 꺼짐, 개인정보 마스킹 |
| actuator | `/health`만 공개, 나머지 401 |
| CORS | 운영 도메인만 |
| 에러 | 스택트레이스 응답 0(prod에서 재확인) |
| time_zone | JVM `Asia/Seoul`, MySQL `+09:00` |
| 청소기 | 5분 스케줄 등록 확인·단일 인스턴스 가정 문서화 |
| 파일 상한 | multipart 2 MB(CSV)·사진 상한 |
| 기동 | prod 프로파일로 ERROR 0·WARN 허용목록 밖 0 |

### 3-4 백업·복구 리허설
`mysqldump` → 새 스키마에 복원 → 복원본으로 run-all.sh 1회 → 결과 동일. 소요 시간·파일 크기 기록(정리.md §5 배포 체크리스트에 절차 고정).

### 3-5 스모크 부하
동시 20 사용자 × (로그인 → 코스 조회 → 미션 3단계 1회) 를 newman `--parallel` 또는 JUnit 스레드로 3분. 기대: 5xx 0·교착 0·평균 응답 < 500ms·HikariCP 대기 0·커넥션 누수 0. 성능 목표가 아니라 **동시성 결함 탐지**가 목적.

### 3-6 인수인계 문서
`인수인계_temple-stamp_최종.md` 한 장: 스택·표 목록·API 91·설정값 목록(`temple.*` 전부, 기본값·의미)·운영 절차(역할 부여 SQL·needs_review 처리·청소기 FAILED 처리·원고 CSV 반입·QR 회전)·배포 체크리스트·미결(결제·ShedLock·중간본·탈퇴 유예). 프론트 전달용 `정리.md` §4를 별도 파일 `frontend-handoff.md`로 뽑는다(지금까지는 §4 append만).
